# AI 해석기 프롬프트 변경 기록

`gemini_interpreter.py` 의 프롬프트(Gemini 에 주는 지시문)를 바꿀 때마다 무엇을 왜 바꿨고 결과가 어떻게 달라졌는지 남긴다.

비교 방법: 같은 시험 사례를 바꾸기 전·후 프롬프트로 똑같이 판단하게 하고 정답 수·위험 자동입력·응답 시간을 비교한다.

```bash
git show <이전 커밋>:gemini_interpreter.py > /tmp/old.py
python prompt_eval.py --module /tmp/old.py   # 바꾸기 전
python prompt_eval.py                        # 바꾼 후
```

- 판단 규칙은 서버(navigator)와 같다: 0.50 이상·1·2위 차이 0.10 이상이면 번호 누름, 0.30~0.50 이면 재질문, 0.30 미만이면 이전 단계 확인·종료
- `--timeout 20`(기본): Gemini 답을 20초까지 기다려 프롬프트 자체의 정확도를 본다. 실제 통화 조건의 속도는 `--timeout 4` 로 따로 잰다
- 위험 자동입력: 기대와 다른 번호를 누른 경우 (재질문·누르지 않음은 위험이 아님)
- 무료 키는 응답 시간이 크게 흔들린다. 한 번 측정한 값이므로 1~2건 차이는 오차일 수 있다

## v0.4 (2026-10-27)

### 바꾼 이유
1. 프롬프트 예시가 KB국민은행 메뉴(분실신고 `*`, 빠른 말 서비스 `#`, 잔액조회, 자기앞수표 등)에 맞춰져 있었다. 기관마다 ARS 가 다르므로 특정 기관 예시를 빼야 한다 (준성님 요청)
2. 이번 단계에 목적에 맞는 선택지가 없을 때 어떻게 할지 규칙이 없었다. 모델이 비슷한 선택지에 0.3~0.5 를 주어 재질문만 반복하거나, 돌아갈 곳이 없는데도 끝나 버렸다 (준성님 요청: 이전 단계로 돌아가거나 상담사 연결로 이어지게)

### 바꾼 내용

| 위치 | 바꾸기 전 (v0.3) | 바꾼 후 (v0.4) |
| --- | --- | --- |
| 공통 (STT 오타) | 예: '하드'→'카드', '상담소'→'상담사', '자기 학습표'→'자기앞수표', '텍스'→'팩스' | 앞뒤 문맥에 맞는 비슷한 발음의 업무 용어로 추정 (예: '상담소'→'상담사') |
| 공통 (신규) | 없음 | 특정 기관의 메뉴 구성·번호를 안다고 가정하지 않고, 이번 안내에 들린 내용만으로 판단 |
| 분류 (`*`·`#` 선택지) | 예: '분실신고 금융사기는 *', '빠른 말 또는 쉬운 말 서비스는 #' | 예: '○○ 신고는 별표', '○○ 서비스는 샵 버튼'. 이동·다시 듣기 키일 때만 분리 |
| 분류 (category 예시) | '잔액조회'→'잔액 조회', '결제일 변경'→'카드 결제일 변경' | '전 단계'·'이전 메뉴'는 back_key. 안내에 없는 업무 범위를 덧붙이지 않음 |
| 분류 (결과 안내) | '금액은 ~원입니다' 등은 다시 듣기·전 단계가 있어도 result | '잔액은 ~원' 추가, 다른 업무 선택지가 뒤에 붙어도 result |
| 점수 (대상 비교) | 예: '카드값 얼마야' 에 '잔액조회'(통장)는 0.3 미만 | 목적과 선택지의 대상이 다르면 같은 단어가 있어도 낮게 (기관 이름 없는 일반 예시) |
| 점수 (맞는 선택지 없음, 신규) | "상담원 연결은 다른 길이 없어 보일 때만 높게" 한 줄 | 업무 선택지는 모두 0.3 미만, 억지로 고르지 않음. 상담원 연결은 `<no_match>` 에 따라: 이전 단계 확인이면 0.2 이하, 상담원 연결이면 0.6 |
| 상담사 전달 문장 예시 | '카드 분실 신고 건으로 … 카드 업무 > 카드 분실 신고' | '○○ 발급 건으로 … ○○ 업무 > ○○ 발급' |

`<no_match>` 는 코드가 정해서 프롬프트에 넣는다 (`_no_match_policy`).

| 상황 | `<no_match>` | 서버 동작 |
| --- | --- | --- |
| 하위 메뉴, 이전 메뉴·처음으로 키 있음 | 이전 단계 확인 | 모든 선택지 0.3 미만 → 이전 계층의 다른 선택지 확인 |
| 첫 메뉴 (돌아갈 곳 없음) | 상담원 연결 | 상담원 연결 0.6 → 상담원 연결 키 누름 |
| 돌아가는 키가 없는 메뉴 | 상담원 연결 | 위와 같음 |
| 이전 계층을 다시 확인하는 중 / 이미 들은 메뉴에 다시 도착 | 상담원 연결 | 위와 같음 |
| 상담원 연결 선택지가 없음 | (점수 조정 없음) | 서버 규칙대로 이전 단계 확인 또는 not_found |

코드 안전장치 (프롬프트와 별개, 모델이 규칙을 놓쳐도 적용)
- 목적에 맞는 업무 선택지가 없을 때 상담원 연결 점수를 위 표대로 맞춘다 (`_apply_no_match`). 목적이 상담원 연결이면 건드리지 않는다
- 결과 문구('잔액은 ~원', '발송됩니다' 등)가 분명하면 모델이 메뉴로 보더라도 결과로 본다. 업무시간 외 안내도 규칙으로 한 번 더 확인
- 목적에 맞는 선택지가 번호 없이 들리면 모든 선택지를 0.40(재질문)으로 둔다

### 결과 비교

시험 사례 31개: 건강보험증 발급 평가 10개(`nhis_*`), 실제 통화 녹취 STT 문장 17개(`real_*`), 맞는 선택지가 없는 경우 4개(`nomatch_*`, 이번에 추가). Gemini `gemini-3.5-flash-lite`, 생각 수준 MINIMAL, 대기 20초.

| | v0.3 | v0.4 (1차) | v0.4 (보완 후) |
| --- | --- | --- | --- |
| 전체 정답 | 27/31 | 26/31 | **31/31** |
| 건강보험 평가 | 10/10 | 9/10 | 10/10 |
| 실제 통화 문장 | 16/17 | 14/17 | 17/17 |
| 맞는 선택지 없음 | 1/4 | 3/4 | 4/4 |
| 위험 자동입력 | 0 | **1** | 0 |
| 응답 시간 p50 / p95 | 7.1초 / 12.4초 | 6.0초 / 10.7초 | 3.7초 / 9.3초 |

응답 시간은 프롬프트보다 그 시각 무료 Gemini 서버 상태 영향이 크다 (같은 날 "hi" 한 마디에 7~8초). 실제 통화 조건(4초)의 속도는 서버가 정상일 때 다시 잰다.

### v0.4 1차에서 발견해 보완한 것
- **위험** `real_kb_balance`: 잔액 안내 뒤 "잔액 조회는 3번" 이 이어지자 모델이 메뉴로 보고 3번을 눌렀다 (같은 업무를 다시 시작). 결과 문구가 분명하면 결과로 보도록 규칙·프롬프트 보완
- `real_nhis_hours`: 업무시간 외 안내를 info 로 분류 → 규칙으로 out_of_hours 확인
- `nhis_card_003`: 번호가 잘린 '건강보험증 발급' 때문에 모든 선택지를 0.3 미만으로 내려 재질문 대신 종료로 갔다 → 0.40(재질문)으로 고정
