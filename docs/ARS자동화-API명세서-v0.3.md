## 1. 개요

### 1.1 설계 원칙

1. 서버는 기관의 메뉴 구조를 사전에 알지 못한다. 통화 중 들은 안내만으로 다음 행동을 결정한다.
2. 앱은 통화에 참여하지 않는다. 서버가 ClawOps 070 번호로 기관 ARS 에 직접 발신하고, 앱은 진행 상황을 이벤트로 수신한다. ARS 소리 듣기와 상담원 연결은 오디오 채널(4.5)로 지원한다 **[검증 필요]**.
3. 상태 머신이 전화 제어를 담당하고, AI 는 의미 판단만 수행한다. AI 는 안내를 해석한 결과를 전달하며, 키 전송·발화·종료는 서버의 상태 머신과 메뉴 라우터, 사용자 조작만 실행한다.
4. 민감정보 입력 요청을 감지하면 AI 처리를 멈추고 사용자가 앱 키패드로 직접 입력하게 한다. 서버는 입력값을 톤으로 전달만 하고 저장하지 않으며, AI 에 전달하지 않는다. (검증 항목 참조)
5. 결제·계약 체결·서비스 해지 최종 승인, 금융·의료 관련 중요 판단에 해당하는 선택은 자동으로 키를 전송하지 않고 사용자에게 재질문한다.
6. AI 도우미 사용과 목적은 통화 시작 시 정한다. 서버는 통화 중간에 사용자 음성 스트림을 중계하지 않으므로, 일반 통화를 AI 도우미 통화로 바꾸거나 AI 도우미 통화를 사용자 직접 통화로 바꾸지 않는다.

### 1.2 시스템 구성

```
[앱] ──REST──────────▶ [API 서버] ──Voice Agent SDK──▶ [ClawOps] ──070 발신──▶ [기관 ARS]
  ◀─WebSocket(이벤트)──┤        │
  ◀▶WebSocket(오디오)──┘        ├── STT : ARS 음성 → 텍스트 (서버 내 로컬 처리)
                               ├── AI 슬롯필링 [AI] : 안내 분류, 선택지 정규화, 목적-선택지 신뢰도
                               └── 메뉴 라우터 : 누를 키 결정, 이전 계층 확인, 반복 감지
```

### 1.3 MVP 범위

| 구분 | 항목 |
| --- | --- |
| 포함 | 전화번호 입력, 목적 음성 입력(발신 시), 다시 말하기(첫 번호 전), ARS 실시간 탐색, 자막·경로·상태·신뢰도 표시, 사용자 확인 요청, 직접 선택, 민감정보 사용자 직접 입력(서버 비저장), 결과 요약·핵심 값, ARS 소리 듣기 **[검증 필요]** |

### 1.4 사용 흐름

앱은 일반 전화처럼 사용한다. 사용자가 발신할 때 ARS Agent 를 켜고 목적을 말한 경우에만 본 API 를 호출하며, 그 외에는 단말의 일반 전화로 발신한다. 서버는 기관을 사전에 구분하지 않고, 사용자가 입력한 전화번호로 발신한다.

흐름: 번호 입력·ARS Agent 켜기 → 목적 말하기 → 세션 생성(발신) → AI 가 첫 메뉴부터 탐색 → 결과 확인(`agent_done`) → 사용자가 통화 종료

- 목적을 말하면 AI 가 이해한 목적을 한 문장(`goal_summary` **[AI]**, 예: "계좌 잔액을 확인해 드릴게요.")으로 보여 주고 승인 없이 바로 진행한다. 다르게 이해했으면 첫 번호를 누르기 전까지 다시 말한다(`revise_goal`). 첫 번호를 누른 뒤에는 재질문에 답하거나(`answer`·`select`) 직접 선택(`key`)한다.
- ARS 소리는 통화 중 아무 때나 켜고 끌 수 있다(4.5). 소리를 켜도 AI 탐색은 그대로 진행한다.
- 피그마의 "직접 통화하기"는 세션을 종료(`cancel`)한 뒤 앱이 단말 일반 전화로 같은 번호에 다시 거는 것으로 처리한다 (8장 8번).

시연 대상은 국민건강보험공단(1577-1000), KB국민은행(1588-9999)이며 서버는 이 정보를 별도로 보유하지 않는다.

## 3. 세션 상태

### 3.1 상태 (`status`)

상태는 변경될 때 `status_changed` 이벤트로 전송한다. 상태가 같아도 안내 문장(`message`)이 바뀌면 전송한다 (예: `selecting` 에서 "누를 번호를 고르고 있습니다." → "'잔액조회' 메뉴를 선택합니다.").

| status | 화면 표시 | 전환 시점 |
| --- | --- | --- |
| `dialing` | 연결 중 | 발신 직후 |
| `listening` | 메뉴 듣는 중 | 상대 응답 직후, 키 전송 직후, 사용자 응답 처리 직후. ARS 안내를 듣고 인식·분류하는 동안 머문다 |
| `selecting` | 번호 입력 중 | 안내가 메뉴·확인 질문으로 분류되어 AI 가 판단을 시작할 때. 키를 전송하면 `listening`, 재질문하면 `awaiting_user`, 맞는 메뉴가 없으면 `ended(not_found)` 로 넘어간다 |
| `awaiting_user` | 확인 필요 / 직접 입력 필요 | 사용자 요청(`request`) 응답 대기. 화면은 `request.kind` 에 따라 재질문 또는 키패드를 표시한다 |
| `listening_result` | 결과 듣는 중 | 키 전송 후 들어온 안내가 선택지가 아닌 조회 결과·완료 안내로 분류됨 |
| `agent_done` | 업무 완료 | 결과 요약(`summary(result)`) 전송 직후. AI 탐색은 끝나고 통화는 유지된다. 사용자는 결과를 확인한 뒤 통화를 종료(`cancel`)한다. 이후 ARS 안내는 자막으로만 전송한다. 민감정보 안내는 6.3 과 같이 처리하고, 사용자가 직접 누른 키(`key`)에 대한 입력 오류 안내는 `input_rejected` 로 알린다 (재질문 없음) |
| `waiting_agent` | 상담원 연결 대기 | 대기 안내·대기 음악 감지 |
| `connected_to_agent` | 상담원 연결됨 | 상담원 음성 감지. AI 처리를 중단하고 사용자가 오디오 채널(4.5)로 상담원과 통화한다 **[검증 필요]** |
| `ended` | 종료 | 통화 종료. `end_reason` 참고 |

상태 흐름

- 기본: `dialing` → `listening` → `selecting` → `listening` → … 반복 → `listening_result` → `agent_done` → (`cancel`) `ended`
- 판단 보류: `selecting` → `awaiting_user` → (응답) → `selecting` 또는 `listening`
- 민감정보: `listening` → `awaiting_user` → (입력) → `listening`
- 상담원: `listening` → `waiting_agent` → `connected_to_agent` → `ended`

### 3.2 종료 사유 (`end_reason`)

`outcome` 은 4.4 결과 조회의 값이다.

| end_reason | 의미 | outcome |
| --- | --- | --- |
| `completed` | 목적에 해당하는 결과 안내를 수신한 뒤 사용자 또는 ARS 가 통화를 종료 (결과 요약을 마치기 전에 ARS 가 끊은 경우 포함, 7장 7항) | `success` |
| `agent_call_ended` | 상담원 연결 후 사용자 또는 상담원이 통화를 종료 **[검증 필요]** | `partial` |
| `message_sent` | ARS 가 문자·알림톡 발송 후 종료 | `partial` |
| `user_input_timeout` | 사용자 응답(민감정보 직접 입력, 재질문) 대기 중 ARS 가 통화를 종료 | `failed` |
| `out_of_hours` | 업무시간 외 안내 | `failed` |
| `ars_rejected` | 본인 확인 실패 등 ARS 측 거절 | `failed` |
| `not_found` | 현재 계층과 이전 계층 모두 목적에 맞는 선택지가 없음 (7장 탐색 규칙) | `failed` |
| `loop_detected` | 반복 한도 초과. 현재는 반복을 재질문(`loop`)으로 처리하여 이 사유로 종료하지 않는다 **[검증 필요]** (8장 13번) | `failed` |
| `user_canceled` | 결과 요약 전, 상담원 연결 전에 사용자가 중단 | `failed` |
| `no_answer` / `busy` / `failed` | 상대가 받지 않음 / 통화 중 / 발신 오류·그 밖의 통화 단절 | `failed` |
| `max_duration` | 상대가 받은 뒤 최대 통화 시간(600초) 초과 | `failed` |

## 4. API

### 4.1 세션 생성

`POST /v1/sessions`

요청 헤더: `X-App-Key`

```json
{
  "phone_number": "1588-9999",
  "goal": "내 통장 잔액을 알고 싶어"
}
```

| 필드 | 필수 | 설명 |
| --- | --- | --- |
| `phone_number` | O | 사용자가 입력한 전화번호. 서버가 숫자만 남겨 정규화한다 |
| `goal` | O | 사용자가 음성으로 말한 목적의 단말 STT 결과 텍스트. 없으면 `400 invalid_request` |

응답 `201`

```json
{
  "session_id": "ses_4b8e21",
  "session_token": "st_...",
  "events_url": "wss://{host}/v1/sessions/ses_4b8e21/events",
  "audio_url": "wss://{host}/v1/sessions/ses_4b8e21/audio",
  "phone_number": "15889999",
  "status": "dialing",
  "goal_summary": "계좌 잔액을 확인해 드릴게요."
}
```

`goal_summary` 는 AI 가 이해한 목적을 한 문장으로 요약한 **[AI]** 값이다 (9.1 `summarize_goal`). 승인을 묻는 문장이 아니며, 앱은 화면과 음성으로 안내만 한다.

서버는 승인 없이 즉시 발신하고 첫 메뉴부터 탐색한다. 목적을 바꾸려면 첫 번호를 누르기 전까지 4.3 `revise_goal` 로 새 목적을 전송한다.

서버는 동시에 통화 1건만 처리한다 (ClawOps Trial·Individual 동시통화 한도). 진행 중인 통화가 있으면 `409 invalid_state` 를 반환한다. 상대가 끊은 뒤 마지막 안내와 결과 요약을 처리하는 중인 세션(7장 7항)은 회선을 쓰지 않으므로 진행 중으로 보지 않는다.

### 4.2 이벤트 수신

`WSS /v1/sessions/{session_id}/events?token={session_token}`

- 연결 시점: 앱은 세션 생성(4.1) 응답을 받은 직후 연결한다. 이렇게 하면 발신 직후의 `status_changed(dialing)` 부터 누락 없이 수신한다.
- `goal_summary` 는 HTTP 응답(4.1, 4.3 `revise_goal`)과 `snapshot` 으로 전달하며, 상대 응답 직후·다시 말하기 직후 `status_changed(listening)` 의 `message` 로도 전송한다.
- 서버 → 앱 단방향 채널이다. 앱의 조작은 4.3 으로 전송한다.
- 연결 직후 서버는 현재 상태 전체를 담은 `snapshot` 이벤트를 전송한다. 재연결 시에도 동일하므로 별도 조회 API 를 두지 않는다. 이미 종료된 세션에 연결하면 `snapshot`(`status=ended`)만 전송하고 서버가 채널을 닫는다.
- 같은 세션에 여러 클라이언트가 동시에 연결할 수 있다.
- 이벤트 목록은 5장에 정의한다.

### 4.3 사용자 조작

`POST /v1/sessions/{session_id}/actions`

요청 헤더: `Authorization: Bearer {session_token}`

```json
{ "type": "answer", "request_id": "req_2", "text": "결제일을 바꾸고 싶어" }
```

| type | 필수 필드 | 설명 |
| --- | --- | --- |
| `answer` | `request_id`, `text` | `kind=clarification` 요청에 대한 음성 답변(단말 STT 결과)을 전달한다. 질문과 답변을 목적에 반영하고(**[AI]** `merge_answer`), 마지막 키 전송 이후 들은 메뉴가 있으면 그 메뉴를 다시 판단한다. 들은 메뉴가 없으면(음성 응답 요구 등) `listening` 으로 돌아가 다음 안내를 기다린다. `critical_action` 에는 사용할 수 없다 |
| `select` | `request_id`, `key` | `kind=clarification` 요청에 포함된 후보 중 하나를 직접 고른다 (보조 수단). 고른 키를 전송하고 `listening` 으로 돌아간다. 후보에 없는 키는 `400 invalid_request` |
| `key` | `key` | 직접 선택. 지정한 키(`[0-9*#]` 1~4자)를 AI 판단과 무관하게 전송한다. 대기 중인 재질문은 닫고, 이전 계층 복귀 중이면 복귀를 멈춘다. AI 탐색 중이면 `listening` 으로 돌아가고 AI 의 메뉴 판단을 10초간 보류하며(결과·상담원·종료 안내는 보류 중에도 처리), 보류가 끝나면 그동안 들은 가장 최근 메뉴를 판단한다. 업무 완료(`agent_done`) 뒤에는 키만 전송한다. 상대가 받기 전에는 `409 invalid_state`, 민감정보 입력 요청이 열려 있으면 `409 sensitive_input_blocked` |
| `secure_input` | `request_id`, `digits` | `kind=secure_input` 요청에 대한 응답. 사용자가 앱 키패드로 입력한 숫자(`[0-9*#]` 1~20자)를 전달한다. 톤 전송 완료 후 응답한다 (6.3 처리 규칙) |
| `revise_goal` | `text` | 다시 말하기 (피그마 03). 첫 번호를 누르기 전까지만 받는다. `text` 는 새 목적(단말 STT 결과). 대기 중인 재질문을 닫고, 첫 메뉴를 들었으면 새 목적으로 다시 판단하며(아직 듣지 못했으면 다음 안내를 기다린다), 응답으로 새 `goal_summary` **[AI]** 를 반환한다. 민감정보 입력 요청은 유지한다. 첫 번호를 누른 뒤에는 `409 invalid_state` |
| `cancel` | — | 통화를 종료한다. `end_reason` 은 상담원 연결 중이면 `agent_call_ended`, 결과 요약 뒤면 `completed`, 그 외에는 `user_canceled` |

응답 `200`

```json
{ "accepted": true, "key_sent": "3" }
```

`revise_goal` 의 응답

```json
{ "accepted": true, "status": "listening", "goal_summary": "이번 달 카드 결제 금액을 확인해 드릴게요." }
```

### 4.4 결과 조회

`GET /v1/sessions/{session_id}/result`

요청 헤더: `Authorization: Bearer {session_token}`

통화가 진행 중이면 `202`, 종료되면 `200` 을 반환한다.

```json
{
  "outcome": "success",
  "end_reason": "completed",
  "summary": "잔액조회 결과, 출금 가능 금액 1,234,000원으로 안내받았습니다.",
  "key_info": [ { "label": "출금 가능 금액", "value": "1,234,000원" } ],
  "handoff_script": null,
  "path": [ "PathStep (6.2)" ],
  "duration_sec": 74
}
```

| 필드 | 설명 |
| --- | --- |
| `outcome` | `success` / `partial` / `failed` (3.2) |
| `summary` | 업무 결과 한 문장 **[AI]** |
| `key_info` | ARS 가 안내한 핵심 값 목록 (`label`: 항목, `value`: 값). 결과 화면의 표로 표시한다. 없으면 빈 배열 **[AI]** |
| `handoff_script` | 상담사에게 전달할 문장 **[AI]** |
| `path` | 실제로 지나온 탐색 경로 (사용자가 직접 선택한 단계 포함) |
| `duration_sec` | 상대가 받은 때부터 종료까지의 통화 시간(초) |

### 4.5 오디오 채널 (ARS 소리 듣기·상담원 연결) **[검증 필요]**

`WSS /v1/sessions/{session_id}/audio?token={session_token}`

앱이 ARS 소리를 듣고(피그마 "ARS 소리 켜기"), 상담원 연결 시 사용자가 상담원과 통화하기 위한 오디오 채널이다. 서버는 음성 인식을 위해 이미 수신하고 있는 통화 음성을 연결된 앱에 그대로 전달하며, 사용자 음성은 상담원 연결 중에만 통화로 전달한다. ClawOps 측 통화는 070↔기관 통화 1건이며, 통화 전환(`call.transfer`)·중계 통화는 추가 통화를 생성하여 동시통화 한도(Trial·Individual 1건)를 초과하므로 사용하지 않는다.

| 항목 | 내용 |
| --- | --- |
| 연결 시점 | 통화 중 아무 때나. 연결하면 소리 켜기, 연결을 끊으면 소리 끄기. 서버는 연결된 순간부터의 음성을 전송하며 이전 음성은 전송하지 않는다 (놓친 안내는 자막으로 확인) |
| 형식 | 바이너리 프레임, G.711 μ-law 8kHz mono, 20ms(160바이트) 단위. ClawOps 미디어 규격과 동일하여 서버에서 변환 없이 전달한다 |
| 서버 → 앱 | 통화 수신 음성(ARS·상담원). 연결되어 있는 동안 계속 전송한다 (초당 약 8KB). 앱 수신이 1초(50프레임) 이상 밀리면 밀린 동안의 프레임은 버린다 |
| 앱 → 서버 | 사용자 마이크 음성. `connected_to_agent` 상태에서만 통화로 전달하고, 그 외에는 버린다. 서버는 받은 데이터를 160바이트 단위로 나누어 전달하며, 160바이트에 못 미치는 나머지는 버린다 |
| 상태·탐색 영향 | 소리를 켜고 끄는 것은 상태와 AI 탐색에 영향을 주지 않는다. 별도 조작(4.3)은 두지 않는다 |
| AI 처리 | `connected_to_agent` 부터 STT·해석 처리를 중단한다. 오디오는 중계만 하며 저장하지 않는다 |
| 앱 요구사항 | 마이크 권한, 스피커 재생, 에코 제거(단말 음성 통화 모드 사용) |

검증 항목

- 이 방식으로 ARS 소리 듣기와 상담원 연결을 지원할지 여부. 서버가 통화 오디오를 앱으로 중계하는 방식이므로, 통화 중간 스트림 중계를 하지 않기로 하면 두 기능 모두 제외된다 (8장 5번)
- 서버 경유로 추가되는 지연. AI 처리를 거치지 않으므로 추가 지연은 서버 경유 네트워크 구간에 한정되며, 서버를 국내 리전에 두면 일반 통화 대비 체감 차이가 작을 것으로 예상한다. 실통화로 측정한다
- ClawOps 가 전달하는 프레임 크기가 20ms(160바이트)인지 실통화로 확인한다
- 단말 에코 제거 성능, 앱 백그라운드 전환 시 오디오 유지

## 5. 이벤트

### 5.1 메시지 형식

```json
{ "event": "caption", "at": "2026-10-24T09:00:31+09:00", "data": { } }
```

이벤트 채널이 끊긴 뒤 재연결하면 서버는 `snapshot` 으로 현재 상태 전체를 전송한다. 앱은 누락된 이벤트를 따로 보정하지 않고 `snapshot` 으로 화면을 다시 구성한다.

사용자에게 보여주거나 들려줄 문장은 별도 이벤트로 분리하지 않고, 해당 이벤트의 `message` 필드로 전달한다. 앱은 `message` 를 화면에 표시하고 음성으로 읽는다. 문장이 없는 이벤트(`caption`, `path_updated` 등)는 화면 갱신만 한다.

| 이벤트 | `message` 예시 | 음성 안내 |
| --- | --- | --- |
| (4.1 응답, 4.3 `revise_goal` 응답) `goal_summary` **[AI]** | "계좌 잔액을 확인해 드릴게요." | O |
| `status_changed` | "'잔액조회' 메뉴를 선택합니다." | O |
| `request` (`kind=clarification`) | 재질문 문장 | O |
| `input_rejected` | "번호가 인식되지 않아 다시 시도합니다." | O |
| `request` (`kind=secure_input`) | "주민등록번호 앞 여섯 자리를 직접 눌러 주세요. 입력하신 번호는 저장되지 않습니다." | O |
| `summary` | 업무 결과 한 문장 (`summary` **[AI]**) | O |
| `ended` | 종료 사유 안내 | O |

### 5.2 이벤트 목록

모든 이벤트는 해당 정보가 생성·변경될 때만 전송한다.

| event | 전송 시점 | data | 화면 반영 |
| --- | --- | --- | --- |
| `snapshot` | 이벤트 채널 연결·재연결 직후 1회 | 현재 `status`, `message`, `goal`, `goal_summary`, `path`, `captions`, `pending_request`, `summary`, `end_reason` | 화면 복구 |
| `status_changed` | 상태 또는 안내 문장 변경 시 | `status`, `message` | 상태와 현재 진행 단계를 한 문장으로 표시 |
| `caption` | ARS 안내 한 단계(단락)가 끝났다고 판단될 때 | Caption (6.1) | 단계별 ARS 자막 추가 |
| `path_updated` | AI 또는 사용자가 키를 선택하여 전송한 직후 | PathStep (6.2) | 이동한 경로와 신뢰도 갱신 |
| `request` | 사용자 응답이 필요할 때 (재질문, 민감정보 직접 입력) | UserRequest (6.3) | `kind` 에 따라 재질문 화면 또는 키패드 화면 표시 |
| `input_rejected` | 키 전송 후 ARS 가 입력 오류·입력 시간 초과를 안내했을 때 | `keys`(직전 전송 키. 민감정보 입력값에 대한 오류이면 `null`), `actor`, `ars_prompt`, `retry_count`, `message` | "입력이 인식되지 않아 다시 시도합니다" 표시 |
| `summary` | 목적 달성 또는 상담원 연결 단계 도달 시 | Summary (6.4) | 결과·핵심 값 표·전달 문구 표시 |
| `ended` | 통화 종료 시 | `end_reason`, `message`, `detail`(선택. `not_found` 처럼 서버 판단으로 종료한 경우의 근거 문장) | 종료 처리 |
| `error` | 오류 발생 시. 현재 서버가 전송하는 경우는 없다 **[검증 필요]** (8장 14번) | `code`, `message` | 오류 표시 |

`summary` 와 `ended` 는 별도 이벤트로 분리한다. 결과 요약 뒤에도(`agent_done`), 상담원 연결 뒤에도 통화는 유지되므로 요약 전송이 곧 통화 종료를 의미하지 않는다.

`ended` 는 세션의 마지막 이벤트이며, 이후에는 어떤 이벤트도 전송하지 않는다.

`input_rejected` 는 서버가 보낸 키에 대한 ARS 의 첫 반응이 입력 오류 안내일 때만 전송한다. 키를 누르지 않은 상태에서 ARS 가 안내하는 "입력 시간이 초과되었습니다"(사용자 응답 대기 중 ARS 의 대기 시간 경과 등)와 키보다 먼저 시작된 오류 안내(7장 8항)는 `input_rejected` 가 아닌 `caption` 으로 전송한다.

## 6. 데이터 모델

### 6.1 Caption

ARS 안내 한 단계(단락)를 하나의 자막으로 전송한다. ARS 안내 한 단락은 한 번만 전달한다. 전용 이벤트로 처리하는 안내(입력 오류 안내 → `input_rejected.ars_prompt`, 민감정보 요청 → `request.ars_prompt`)는 `caption` 으로 중복 전송하지 않는다. 서버는 안내가 일정 시간(기본 1.2초) 멈추면 단락이 끝난 것으로 판단하고, 그 단락의 인식 문장을 합쳐 전송한다. 키를 전송하면 그때까지 듣던 끝나지 않은 단락은 버린다 (키 입력으로 ARS 안내가 끊기거나 바뀌므로 앞뒤 안내가 한 자막으로 섞이지 않게 한다).

```json
{ "step": 1, "speaker": "ars", "text": "잔액조회는 3번, 거래내역조회는 4번, 상담직원 연결은 0번을 눌러 주십시오.", "at": "2026-10-24T09:00:31+09:00" }
```

`speaker`: `ars` / `system`. `step` 은 해당 안내 이후 전송되는 PathStep 의 `step` 과 같다.

### 6.2 PathStep

키 전송 1회마다 1건을 전송한다. 해당 단계에서 들은 선택지와 선택 결과를 구조화하여 담고, 화면 표시용 요약 문자열(`text`)을 함께 제공한다. 이전 계층 복귀를 위해 누른 키(이전 메뉴, 처음으로)도 기록한다. 민감정보 입력(`secure_input`)과 서버가 안내를 다시 듣기 위해 자체적으로 누르는 키(7장 3항, 6.3 무응답 처리)는 기록하지 않는다.

```json
{
  "step": 1,
  "text": "잔액조회·거래내역조회·상담직원 연결 중 잔액조회(3) 선택",
  "options": [
    { "key": "3", "label": "잔액조회", "category": "잔액 조회" },
    { "key": "4", "label": "거래내역조회", "category": "거래내역 조회" },
    { "key": "0", "label": "상담직원 연결", "category": "상담원 연결" }
  ],
  "selected": { "key": "3", "label": "잔액조회", "category": "잔액 조회", "confidence": 0.92 },
  "actor": "ai"
}
```

| 필드 | 설명 |
| --- | --- |
| `actor` | `ai`(서버가 자동으로 선택) / `user`(사용자가 직접 선택) |
| `options` | 해당 단계에서 들은 선택지. `label` 은 ARS 가 말한 선택지 이름 그대로 **[AI]**, `category` 는 그 선택지를 정규화한 카테고리 **[AI]** (9.1 `classify`). 안내에서 들은 이동 키(이전 메뉴·처음으로·다시 듣기)도 포함하며, 이동 키의 `category` 는 `null` 이다 |
| `selected.confidence` | AI 가 이 선택지를 고른 근거가 된 신뢰도 **[AI]** (9.1 `score`). 사용자가 직접 고른 경우와 이전 계층 복귀·무응답 처리처럼 신뢰도로 고르지 않은 키는 `null` |
| `text` | 서버가 `label` 을 이어 만든 표시 문자열. 업무 선택지를 고른 경우 "들은 선택지 중 고른 선택지(키) 선택", 이동 키는 "이전 메뉴(*) 선택", 안내에 없던 키는 "9 입력" 형식 |

앱은 진행 화면에서 `text` 를 표시하고, 결과 화면·확인 화면에서 `options` 를 사용한다. 화면에는 `label` 을 표시한다.

### 6.3 UserRequest

서버가 사용자 응답을 기다리는 모든 경우를 하나의 `request` 이벤트로 전송한다. 공통 필드와 `kind` 별 필드로 구성한다. 동시에 대기하는 요청은 최대 1건이다.

| 공통 필드 | 설명 |
| --- | --- |
| `request_id` | 요청 식별자. 응답(4.3) 시 함께 전송한다 |
| `kind` | `clarification`(재질문) / `secure_input`(민감정보 직접 입력) |
| `message` | 화면 표시·음성 안내 문장 |
| `expires_at` | 응답 기한 |

| kind | 응답 방식 (4.3 `type`) | 응답 처리 |
| --- | --- | --- |
| `clarification` | `answer`(음성 답변) / `select`(후보 선택) | 답변을 목적에 반영하여 AI·메뉴 라우터가 재판단 |
| `secure_input` | `secure_input`(키패드 숫자) | 톤 변환·전송 후 즉시 폐기. AI·로그 경로를 거치지 않음 |

응답 타입을 `kind` 별로 분리하는 이유는 민감정보 입력값이 일반 응답 처리 경로(AI 재판단, 요청 로그)로 유입되지 않도록 서버에서 경로를 물리적으로 분리하기 위함이다.

요청이 열려 있을 때 조작별 처리

| 조작·사건 | 재질문 (`clarification`) | 민감정보 (`secure_input`) |
| --- | --- | --- |
| `answer` | 목적 보충 후 재판단 (`critical_action` 은 `409`) | `409 invalid_state` |
| `select` | 후보 키 전송 후 `listening` | `409 invalid_state` |
| `secure_input` | `409 invalid_state` | 톤 전송 후 폐기 → `listening` (업무 완료 뒤면 `agent_done`) |
| `key` | 요청을 닫고 키 전송, AI 메뉴 판단 10초 보류 | `409 sensitive_input_blocked` |
| `revise_goal` | 첫 번호 전이면 요청을 닫고 새 목적으로 재판단, 이후 `409` | 첫 번호 전이면 요청을 유지한 채 목적만 바꿈, 이후 `409` |
| `cancel` | 종료 (`user_canceled`) | 종료 (`user_canceled`, 업무 완료 뒤면 `completed`) |
| 응답 없음 | 아래 무응답 처리 | 서버 동작 없음 |
| ARS 가 통화를 끊음 | `user_input_timeout` | `user_input_timeout` |
| ARS 의 입력 시간 초과 안내 | 자막만 전송, 요청 유지 (키 오류가 아님) | 자막만 전송, 요청 유지 |
| ARS 가 메뉴를 다시 읽음 | 요청 유지. 답변이 오면 그 메뉴로 판단 | 요청을 닫고 그 메뉴를 판단 (ARS 가 입력 없이 메뉴로 돌아간 것) |
| 민감정보 안내 수신 | 재질문을 닫고 민감정보 요청으로 바뀜 | 무시 (이미 대기 중) |

#### kind = clarification

AI 가 판단에서 막힌 지점을 해결하기 위해 사용자에게 재질문한다. 사용자는 음성으로 목적을 보충하여 답하며(`answer`), 후보를 직접 고르는 것(`select`)은 보조 수단이다. AI 탐색 중에만 발생하며, 업무 완료(`agent_done`) 뒤에는 발생하지 않는다.

재질문 여부와 `reason` 은 서버가 **[AI]** 신뢰도(9.1 `score`)와 안내 분류(9.1 `classify`)를 기준값과 비교하여 결정한다. `options` 의 `label`·`category`·`confidence` 는 **[AI]** 값이고, `message` 는 서버가 `reason` 별 문장 틀에 `label` 을 넣어 만든다.

근거: PRD 4-2 조건부 흐름("선택 신뢰도가 낮음 → 재질문, 사용자 목적 재전달")을 따랐다. UX 화면설계·MVP IA·PRD 5장·F-ARS-06 은 "후보 메뉴 제시 후 사용자 선택"으로 되어 있어 차이가 있으며, 8장 설계 검증 요청 사항에 포함한다.

```json
{
  "request_id": "req_2",
  "kind": "clarification",
  "message": "결제 대금 조회 / 결제일 변경 중 어느 쪽인가요? 원하시는 업무를 말씀해 주세요.",
  "reason": "ambiguous",
  "options": [
    { "key": "2", "label": "결제 대금 조회", "category": "카드 대금 조회", "confidence": 0.70 },
    { "key": "3", "label": "결제일 변경", "category": "카드 결제일 변경", "confidence": 0.70 }
  ],
  "ars_prompt": "카드 분실 신고는 1번, 결제 대금 조회는 2번, 결제일 변경은 3번을 눌러 주십시오.",
  "expires_at": "2026-10-24T09:01:05+09:00"
}
```

| reason | 발생 조건 |
| --- | --- |
| `low_confidence` | 최고 신뢰도가 0.30 이상 0.50 미만 (불확실). 같은 메뉴에서 1회만 묻고, 답변 뒤에도 0.50 미만이면 불일치로 보고 7장 탐색 규칙을 따른다 |
| `ambiguous` | 신뢰도가 기준(0.50) 이상인 선택지가 둘 이상이고 1·2순위 차이가 0.10 미만 |
| `loop` | 키 전송 결과로 이미 지나온 메뉴에 다시 도착하는 상황이 2회 발생, 또는 AI 가 업무 선택 키를 5회 전송하는 동안 목적 지점에 도달하지 못함. 반복으로 세지 않는 경우는 7장 5항. 응답하면 반복 횟수를 다시 센다 (8장 11번) |
| `unknown_prompt` | 목적만으로는 답을 정할 수 없는 안내. ① 확인 질문에 AI 가 누를 키를 정하지 못함 (예: "이용 중인 카드가 체크카드이면 1번, 신용카드이면 2번"처럼 사용자 정보가 필요한 질문) ② 민감정보 입력 후 ARS 가 입력값을 다시 읽고 "맞으면 1번"으로 확인을 물음 ③ ARS 가 음성으로 답하라고 요구 (7장) |
| `input_rejected` | 같은 단계에서 키 전송 후 ARS 의 입력 오류 안내가 연속 2회 발생. 키가 받아들여져 오류가 아닌 다음 안내가 오면 다시 센다 |
| `critical_action` | 선택지 또는 확인 질문이 결제·계약 체결·서비스 해지 최종 승인, 금융·의료 관련 중요 판단에 해당. 신뢰도와 관계없이 키를 전송하지 않는다 |

신뢰도 구간 **[검증 필요]**

| 최고 신뢰도 | 판단 | 서버 동작 |
| --- | --- | --- |
| 0.50 이상 | 일치 | 1·2순위 차이 0.10 이상이면 키 전송, 미만이면 `ambiguous` |
| 0.30 이상 0.50 미만 | 불확실 | `low_confidence` 재질문 (PRD 4-2 "선택 신뢰도가 낮음 → 재질문") |
| 0.30 미만 | 불일치 | 재질문하지 않고 7장 탐색 규칙(이전 계층 확인 → 종료)을 따른다 |

reason 별 응답 방식

| reason | `options` | 허용 응답 | 비고 |
| --- | --- | --- | --- |
| `low_confidence`, `ambiguous`, `loop`, `input_rejected` | 들은 선택지 (`low_confidence` 는 0.30 이상 상위 3개, `ambiguous` 는 0.50 이상이면서 1순위와 차이 0.10 미만인 후보) | `answer`(기본), `select` | 음성 답변을 목적에 반영하여 재판단한다 |
| `unknown_prompt` | 들은 선택지가 있으면 포함 | `answer`, `select` | 선택지가 없으면 `answer` 만 가능하다. 음성 응답 요구(③)에 답하면 목적에 반영한 뒤 다음 안내를 기다린다 |
| `critical_action` | 해당 선택지 | `select` 만 허용 | 결제·계약·해지 등은 음성 해석 오류로 실행되지 않도록 사용자가 키를 직접 고른다. `answer` 는 `invalid_state` 로 거절한다 |

#### 무응답 처리 (검토 필요, 이런 방식을 할 건지 모르겠음)

사용자가 답하지 않는 동안 ARS 는 자체 입력 대기 시간이 끝나면 메뉴를 다시 읽거나, 몇 차례 반복 후 통화를 종료한다. 서버는 다음 순서로 처리한다.

| 경과 | 서버 처리 | 앱 |
| --- | --- | --- |
| ARS 가 메뉴를 다시 읽음 | 그대로 듣는다. 요청은 유효하게 유지하고, 답변이 오면 그 시점에 판단한다 | 재질문 화면 유지 |
| 15초 | — | 질문을 음성으로 한 번 더 읽어 준다 (단말 처리) |
| 30초 (`expires_at`) | 안내에서 들은 다시 듣기 키를 1회 전송하여 ARS 가 통화를 종료하지 않도록 한다. ARS 가 안내하는 중이면 안내가 끝난 뒤 전송한다. 요청은 계속 유효하다 | 재질문 화면 유지 |
| 60초 | 요청을 무효로 하고 상담원 연결 메뉴로 진행한다. 사용자 응답 없이는 탐색을 이어갈 수 없으므로 상담원에게 넘긴다. 현재 메뉴에 상담원 연결 선택지가 없으면 요청을 유지한 채 계속 듣는다 | `status_changed` 로 `awaiting_user` 가 해제되면 재질문 화면을 닫는다 |

`kind=secure_input` 요청은 대체 동작이 없다. 사용자 응답(민감정보 입력, 재질문) 대기 중 ARS 가 통화를 종료하면 `user_input_timeout` 으로 종료한다.

- ARS 다시 듣기 키 전송은 서버가 필요에 따라 자체적으로 수행하며 앱 조작으로 두지 않는다. 앱의 "다시 듣기"는 받은 질문·자막을 단말에서 다시 읽어 주는 기능이다.

#### kind = secure_input

```json
{
  "request_id": "req_3",
  "kind": "secure_input",
  "label": "주민등록번호 앞 여섯 자리",
  "ars_prompt": "주민등록번호 앞 여섯 자리와 우물정자를 눌러 주십시오.",
  "terminator": "#",
  "message": "주민등록번호 앞 여섯 자리를 직접 눌러 주세요. 입력하신 번호는 저장되지 않습니다.",
  "expires_at": "2026-10-24T09:02:10+09:00"
}
```

| 필드 | 설명 |
| --- | --- |
| `label` | ARS 안내에서 추출한 입력 항목명 **[AI]** |
| `ars_prompt` | ARS 안내 원문 |
| `terminator` | 안내에 종료 키가 포함된 경우 해당 키 **[AI]**. 서버가 입력값 뒤에 붙여 전송한다 |
| `expires_at` | 표시용 기한(60초). 서버는 이 시각에 별도 동작을 하지 않는다 |

처리 규칙

1. 서버는 `secure_input` 요청을 받으면 `digits` 를 메모리에서 DTMF 톤으로 변환하여 ARS 에 전송한 직후 폐기한다. `terminator` 가 있으면 뒤에 붙이되, 사용자가 이미 종료 키까지 누른 경우 중복해 붙이지 않는다. 서버는 입력값의 자릿수만 기억한다(3항 마스킹용).
2. 입력값은 DB·로그·AI·STT 어디에도 전달하지 않는다. 요청 본문은 접근 로그에서 제외한다.
3. 입력 후 ARS 가 입력값을 다시 읽어 주는 안내("입력하신 번호는 … 맞으면 1번"처럼 입력 표현과 확인 표현이 함께 있는 안내)는 서버 내 로컬 STT 결과에서 숫자를 가린 뒤 AI 에 전달하며, 자막으로 전송하지 않는다. 그 밖의 다음 안내에서는 입력 자릿수와 같은 숫자열만 가린 뒤(금액·날짜처럼 자릿수가 다른 숫자는 남긴다) 일반 처리로 돌아간다. 외부 STT 를 사용하는 경우 되읽기 구간은 인식하지 않는다.
4. 해당 구간의 확인 질문은 AI 가 답하지 않고 `request(clarification, unknown_prompt)` 로 사용자에게 묻는다.
5. 서버는 톤 전송을 마친 뒤 `secure_input` 요청의 응답(`200 { "accepted": true }`)을 반환한다. 별도 완료 이벤트는 전송하지 않는다.
6. 입력 후 ARS 가 오입력을 안내하면 `input_rejected(keys=null, actor=user)` 를 전송하고, 메뉴 키의 입력 오류로 세지 않는다(재질문으로 이어지지 않음). ARS 가 입력 안내를 다시 하면 `kind=secure_input` 인 새 `request` 를 전송한다.
7. 민감정보 입력 요청이 열려 있을 때 직접 선택(`key`)으로 입력하면 입력값이 경로(PathStep)에 기록되므로 `sensitive_input_blocked` 로 거절한다.

```json
{
  "kind": "result",
  "summary": "잔액조회 결과, 출금 가능 금액 1,234,000원으로 안내받았습니다.",
  "key_info": [ { "label": "출금 가능 금액", "value": "1,234,000원" } ],
```

## 7. 처리 흐름

서버는 통화가 연결된 시점부터 매 단계 다음 순서를 반복한다.

1. ARS 안내를 STT 로 수신한다. 안내가 멈추면 단락 전체를 `caption` 으로 전송한다.
2. 안내가 끝나면 **[AI]** 가 안내를 아래 표의 분류 중 하나로 분류한다 (9.1 `classify`). 메뉴·확인 질문이면 `status_changed(selecting)` 을 전송하고 판단을 시작한다. 업무 완료(`agent_done`) 뒤에는 민감정보 요청과 사용자가 직접 누른 키의 입력 오류 안내만 처리하고, 나머지는 자막만 전송한다.
3. 키 전송 후 일정 시간(기본 8초) 동안 ARS 가 아무 소리도 내지 않으면 키가 인식되지 않은 것으로 보고, 같은 키를 재전송하지 않고 키를 누른 메뉴에서 들은 재청취(다시 듣기) 키를 전송한다. 그 사이 ARS 가 소리를 냈으면(다음 안내를 하는 중이거나 인식 중) 키를 전송하지 않고 안내가 끝나기를 기다린다. 이전 메뉴의 재청취 키는 다음 메뉴에서 다른 뜻일 수 있기 때문이다.
4. 사용자가 직접 선택(4.3 `key`)한 키에도 2·3항을 동일하게 적용한다. 이 경우 `input_rejected.actor` 는 `user` 이다.
5. 반복(`loop`) 판정은 서버가 키를 전송한 결과로 이미 지나온 메뉴에 되돌아온 경우만 센다. 키를 전송하지 않은 상태에서 ARS 가 입력 대기 시간 초과로 같은 메뉴를 다시 재생하는 경우, 다시 듣기 키로 재생된 경우(3항 포함), 사용자 확인 대기 중 재생된 경우, 입력 오류 뒤 재생된 경우, 이전 계층 복귀로 도착한 경우는 반복으로 세지 않는다.
6. 입력 오류는 같은 단계에서 연속으로 난 경우만 센다. 키가 받아들여져 오류가 아닌 다음 안내가 오면 다시 센다.
7. 상대(ARS·상담원)가 통화를 끊으면, 끊기 직전까지 들은 안내(무음이 오기 전에 끊긴 마지막 단락 포함)의 인식·처리와 결과 요약을 마친 뒤(최대 10초) 종료 사유를 정하고 `ended` 를 전송한다. 끊긴 뒤에 인식한 메뉴에는 키를 전송하지 않으며, 사용자 조작은 `cancel` 외에 `409 invalid_state` 로 거절한다.
8. 서버가 키를 보내기 전에 시작된 안내는 키 이전 상태의 안내로 본다. 그 안내가 메뉴·확인 질문·입력 오류이면 자막만 전송하고 판단·오류 집계에 쓰지 않는다 (AI 판단이 ARS 의 입력 대기 시간보다 늦어 ARS 가 같은 메뉴를 다시 읽기 시작한 뒤 키를 누른 경우, 같은 키를 두 번 보내지 않기 위함). 키를 보내면 그때까지 듣던 끝나지 않은 단락은 버린다(6.1).
9. AI 모듈 호출이 실패하면 서버는 통화를 멈추지 않고 9.3 의 대체 동작으로 진행한다.

#### 분류별 서버 동작 (2항)

분류(왼쪽 열)는 **[AI]** 결과이고, 서버 동작(오른쪽 열)은 서버가 수행한다.

| 분류 | 서버 동작 |
| --- | --- |
| 선택지 안내 | `status_changed(selecting)` → 선택지 정규화·신뢰도 계산 → 탐색 규칙에 따라 판단 → 키 전송(`path_updated`, 신뢰도 포함) 후 `listening`, 또는 `request(clarification)`(→ `awaiting_user`), 또는 `ended(not_found)` |
| 확인 질문 ("맞으면 1번") | `status_changed(selecting)` → 목적과 대조하여 응답 키 전송(**[AI]** `answer_confirm`), 판단 불가 시 `request(clarification, unknown_prompt)` |
| 중요 선택 (결제·계약·해지 최종 승인 등, 확인 질문 포함) | `status_changed(selecting)` → 키를 전송하지 않음 → `status_changed(awaiting_user)` → `request(clarification, critical_action)` → 사용자가 `select` 로 명시적으로 지시한 경우에만 전송 |
| 민감정보 요청 | AI 처리 중단 → `status_changed(awaiting_user)` → `request(secure_input)` → 사용자 입력(`secure_input`) → 톤 전송 → ARS 의 다음 안내부터 처리 재개 |
| 결과 안내 | `status_changed(listening_result)` → `summary(result)` → `status_changed(agent_done)`. AI 탐색을 끝내고 통화는 유지한다. 사용자가 `cancel` 하거나 ARS 가 통화를 끊으면 `ended(completed)`. 결과 요약을 마치기 전에 ARS 가 끊으면 요약을 마친 뒤 `summary(result)` → `ended(completed)` 순서로 전송한다 (`agent_done` 생략, 7항) |
| 상담원 대기 | `status_changed(waiting_agent)` → 대기 중 계속 청취 → 상담원 음성 감지 시 `summary(handoff)` → `status_changed(connected_to_agent)` → 오디오 채널(4.5)로 사용자 통화 **[검증 필요]** |
| 업무시간 외·거절·문자 발송 | 해당 `end_reason` 으로 통화 종료 |
| 음성 응답 요구 (음성봇) | "버튼 메뉴" 등 전환 문구를 음성으로 송출 **[검증 필요]**. 서버 음성 송출(TTS) 구현 전까지는 `request(clarification, unknown_prompt)` 로 사용자에게 알린다 |
| 입력 오류 안내 ("잘못 누르셨습니다", "입력 시간이 초과되었습니다") | 키 전송 후인 경우 `input_rejected` → 같은 단계의 선택지를 다시 듣고 재판단. 같은 단계에서 연속 2회이면 `request(clarification, input_rejected)` |
| 기타 안내 | 자막만 전송 |

직접 선택(`key`) 뒤 10초 보류 중에는 메뉴·확인 질문의 판단만 미루고, 위 표의 나머지 분류는 그대로 처리한다.

#### 탐색 규칙

1. **현재 계층에서 판단한다.** 탐색은 첫 메뉴에서 시작한다. 마지막 키 전송 이후 아직 메뉴를 듣지 못했으면 다음 안내를 기다린다. 다시 말하기(`revise_goal`)는 첫 번호를 누르기 전에만 가능하므로, 다시 말하면 새 목적으로 첫 메뉴를 다시 판단한다.
2. **선택지를 정규화하고 신뢰도로 판단한다.** **[AI]** 가 선택지를 카테고리로 정규화하고(9.1 `classify`) 목적을 각 카테고리에 맞춘 신뢰도를 낸다(9.1 `score`). 1순위가 0.50 이상이고 2순위와 0.10 이상 차이가 나면 해당 키를 전송하고, 차이가 0.10 미만이면 `request(clarification, ambiguous)` 로 묻는다. 1순위가 0.30 이상 0.50 미만이면 `request(clarification, low_confidence)` 로 묻는다 (메뉴당 1회).
3. **맞는 선택지가 없으면 이전 계층을 확인한다.** 1순위가 0.30 미만이거나 `low_confidence` 답변 뒤에도 0.50 미만이면, 이전 계층(직전에 키를 눌러 지나온 메뉴, 사용자가 직접 선택한 단계 포함)에서 이미 고른 선택지를 제외한 나머지의 신뢰도를 계산한다. 0.50 이상인 선택지가 있으면 현재 안내에서 들은 '이전 메뉴' 키로 돌아가고, '이전 메뉴' 키가 없으면 '처음으로' 키와 지나온 키를 차례로 눌러 이전 계층으로 돌아간 뒤 2번부터 다시 판단한다. 이미 고른 선택지는 돌아간 그 계층에서만 제외한다.
4. **그래도 맞는 선택지가 없으면 종료한다.** 이전 계층에도 0.50 이상인 선택지가 없거나, 돌아가는 키가 안내되지 않았거나, 이미 이전 계층 복귀를 한 번 사용한 경우 `ended(end_reason=not_found)` 로 통화를 종료한다. 이전 계층 복귀는 탐색당 1회만 허용한다.

답변이 없으면 6.3 무응답 처리에 따라 60초 뒤 현재 메뉴의 상담원 연결(0)로 진행한다.

## 8. 설계 검증 요청 사항

1. 항목 6.3의 무응답 처리 기준이 적절한지 (수정 필요하면 제안 필요)
2. 목적을 말하면 승인 없이 바로 진행하고, 다르게 이해한 경우 첫 번호를 누르기 전까지만 다시 말하게 하는 방식이 적절한지 (현재: 피그마 03 화면에 따라 승인 단계 없음, 첫 번호 이후 `revise_goal` 은 409. 대안: 통화 중 언제든 허용, 또는 `cancel` 후 재발신)
3. 판단이 불확실할 때 재질문(PRD 4-2)과 후보 메뉴 제시(UX 화면설계·MVP IA·PRD 5장·F-ARS-06) 중 어느 방식을 따를지 (현재: PRD 4-2 재질문을 기본으로, 후보 선택을 보조로 둠)
4. MVP 범위의 "민감정보 입력 제외"가 민감정보 입력이 필요한 업무 자체를 시연·지원 범위에서 제외한다는 의미인지, 민감정보를 수집하지 않는다는 의미인지 (현재: 수집하지 않는다는 의미로 해석하여 사용자 직접 입력·서버 비저장으로 설계)
5. MVP 범위의 "상담원 통화 중계 제외"가 상담원 연결 자체를 제외한다는 의미인지, AI 가 상담원과의 대화에 개입하는 기능을 제외한다는 의미인지. 후자라면 상담원 연결과 ARS 소리 듣기(피그마 "ARS 소리 켜기")를 오디오 채널(4.5)로 지원할지. 통화 중간 스트림 중계를 하지 않기로 하면 두 기능 모두 제외되며, 상담원 연결은 상담원 대기 도달 시 `handoff_script` 를 전달하고 종료하는 방식이 된다 (현재: 4.5 를 검증 필요 상태로 유지. 통화 전환 방식은 동시통화 한도로 불가)
6. 재질문에 사용자가 답하지 않을 때 60초 후 상담원 연결 메뉴로 진행하는 정책이 적절한지 (대안: ARS 가 통화를 종료할 때까지 대기, 즉시 통화 종료) - 또 필요하다면 60초?로 괜찮은지, 주기적으로 요청을 다시 말하고 입력해달라고 전달할지 등.
7. 사용자에게 선택을 맡길 때 화면에 선택지를 보여주고 직접 고르게 하는 방식(`select`, 고른 번호를 그대로 DTMF 로 전송)과 음성으로 답하게 하는 방식(`answer`, 서버가 해석하여 재판단) 중 무엇을 기본 응답 방식으로 할지 (현재: `answer` 기본, 결제·계약·해지 등 `critical_action` 은 `select` 만 허용)
8. AI 도우미 사용과 목적을 통화 시작 시 정하고 통화 중에는 전환하지 않는 구조가 적절한지, 피그마 "직접 통화하기"를 세션 종료 후 단말 일반 전화 재발신으로 처리하는 것이 적절한지 (현재: 통화 중 전환 없음. 피그마 01 의 통화 중 ARS Agent 버튼은 발신 화면으로 옮겨야 함)
9. 맞는 선택지가 없을 때 이전 계층을 1회 확인한 뒤 종료하는 규칙(7장 탐색 규칙)이 적절한지 (대안: 상담원 연결 메뉴로 우회)
10. 신뢰도 구간 기준값(0.50 이상 일치, 0.30~0.50 `low_confidence` 재질문, 0.30 미만 불일치)이 적절한지. AI 모듈의 실제 신뢰도 분포를 보고 조정한다
11. 반복(`loop`) 판정에 사용자가 직접 누른 키로 되돌아온 경우도 포함할지 (현재: 포함. 대안: AI 가 누른 키로 되돌아온 경우만 셈)
12. 업무 완료(`agent_done`) 뒤 사용자가 직접 상담원 메뉴를 고른 경우 상담원 연결 상태로 전환할지 (현재: 대기 안내·상담원 음성을 자막으로만 처리하며 `connected_to_agent` 로 전환하지 않음. 종료 사유는 `completed`. 5번 결정에 따름)
13. `loop_detected` 종료 사유를 유지할지 (현재: 발생 경로 없음. 반복은 `loop` 재질문으로 처리. 대안: 삭제, 또는 `loop` 재질문 무응답 시 종료 사유로 사용)
14. 이벤트·조작을 줄일지 (현재: `input_rejected` 는 안내 문장 전달 용도라 `status_changed.message` 로 합칠 수 있고, `select` 는 `key` 에 `request_id` 를 붙인 형태로 합칠 수 있으며, `error` 이벤트는 전송하는 경우가 없음)
15. 민감정보 입력 대기 중 ARS 가 입력 없이 메뉴로 돌아가면 입력 요청을 닫고 메뉴를 판단하는 규칙(6.3)이 적절한지. AI 가 입력 안내를 메뉴로 잘못 분류하면 입력 요청이 닫히는 위험이 있다 (대안: 사용자가 요청을 직접 닫을 때까지 유지)
16. 통화 중 발생할 수 있는 입력·반응의 경우의 수와 서버 처리는 별도 문서(엣지케이스 점검표)에 정리했다. 누락된 경우가 있으면 추가 요청

## 9. AI 슬롯필링 연동 형식 (팀원 담당)

서버는 AI 슬롯필링 모듈을 아래 7개 함수로 호출한다. 본 장은 입출력 형식만 정의하며, 판단 로직과 모델 선택은 AI 담당 팀원이 정한다. AI 모듈 구현 전까지 서버는 목 데이터(9.4)로 동작한다.

### 9.1 함수 목록

| 함수 | 호출 시점 | 입력 | 출력 |
| --- | --- | --- | --- |
| `summarize_goal` | 세션 생성(4.1), `revise_goal`(첫 번호 전) | `goal`: 사용자 목적 문장 | 이해한 목적 한 문장 (`goal_summary`, 승인 질문이 아님. 예: "계좌 잔액을 확인해 드릴게요.") |
| `classify` | ARS 안내 한 단락이 끝날 때마다 | `text`: 안내 단락 STT 결과 | Prompt (9.2). 선택지마다 `label` 을 정규화한 `category` 포함 |
| `score` | 메뉴 판단 시, 이전 계층 확인 시 | `goal`, `options`: 정규화된 선택지 목록(`label`, `category`), `path`: 지금까지 들은 선택지 중 고른 메뉴의 `category` (직접 선택한 키·이동 키 제외) | 사용자 목적을 각 선택지 카테고리에 맞춘 신뢰도 0~1 (`{"3": 0.92, "4": 0.10}`). 서버는 이 값을 `path_updated.selected.confidence`, 재질문 `options[].confidence` 로 앱에 전송하고 6.3 신뢰도 구간과 비교하여 판단한다 |
| `answer_confirm` | 확인 질문("맞으면 1번") 수신 시 (중요 선택이 아닌 경우) | `goal`, Prompt | 누를 키. 판단 불가 시 `null` (→ `request(clarification, unknown_prompt)`) |
| `merge_answer` | 재질문(`clarification`)에 대한 `answer` | `goal`, `question`: 재질문 문장, `answer`: 사용자 답변 | 답변을 반영한 새 목적 문장 |
| `summarize_result` | 결과 안내 수신 시 | `goal`, `captions`: 탐색 시작 이후 자막 목록 | `{"summary": 업무 결과 한 문장, "key_info": [{"label": 항목, "value": 값}]}` |
| `handoff_script` | 상담원 음성 감지 시 | `goal`, `path_texts`: 안내에서 들은 선택지를 고른 단계의 PathStep `text` 목록 (직접 선택한 키·이동 키·민감정보 입력 제외) | 상담사 전달 문장 (`summary.handoff_script`) |

서버가 수행하는 판단: 신뢰도 구간(0.50·0.30)·차이(0.10) 비교, 반복 감지, 이전 계층 확인과 종료(7장 탐색 규칙), 재질문 문장 틀, 키 전송, 상태 전환. AI 모듈은 키를 직접 전송하지 않는다.

### 9.2 Prompt 형식 (`classify` 출력)

```json
{
  "kind": "menu",
  "options": [
    { "key": "3", "label": "잔액조회", "category": "잔액 조회" },
    { "key": "4", "label": "거래내역조회", "category": "거래내역 조회" },
    { "key": "0", "label": "상담직원 연결", "category": "상담원 연결" }
  ],
  "back_key": "*",
  "home_key": null,
  "repeat_key": "#",
  "agent_key": "0",
  "label": null,
  "terminator": null,
  "critical": false
}
```

| 필드 | 설명 |
| --- | --- |
| `kind` | `menu`, `confirm`, `sensitive`, `result`, `agent_wait`, `agent_human`, `input_error`, `voice_request`, `out_of_hours`, `message_sent`, `rejected`, `info` 중 하나 (7장 분류 표와 대응) |
| `options` | 업무 선택지. '이전 메뉴'·'처음으로'·'다시 듣기' 키는 제외하고 아래 필드로 분리한다. 상담원 연결 선택지는 포함한다 |
| `options[].label` | ARS 가 말한 선택지 이름 그대로 (예: "상담직원 연결") |
| `options[].category` | `label` 을 정규화한 카테고리 (예: "상담사 연결", "상담직원 연결" → "상담원 연결"). 기관마다 다른 표현을 같은 카테고리로 묶어 목적과 비교하기 위한 값이다 |
| `back_key` / `home_key` / `repeat_key` | 안내에 포함된 이전 메뉴·처음으로·다시 듣기 키. 없으면 `null`. 탐색 규칙의 이전 계층 복귀, 6.3 무응답 처리, 7장 3항 재청취에 사용한다 |
| `agent_key` | 상담원 연결 키. 없으면 `null` |
| `label`, `terminator` | `kind=sensitive` 일 때 입력 항목명과 종료 키 |
| `critical` | 결제·계약 체결·서비스 해지 최종 승인 등 중요 선택 여부. 메뉴와 확인 질문 모두에 적용한다 |

### 9.3 연동 규칙

1. 민감정보 입력값(`secure_input.digits`)은 AI 모듈에 전달하지 않는다.
2. ARS 가 입력값을 다시 읽어 주는 안내는 숫자를 `*` 로 가린 문장을 `classify` 에 전달한다.
3. AI 호출에 사용하는 API 키는 서버 환경변수(.env)로 관리하며 앱에 전달하지 않는다.
4. `classify` 와 `score` 는 ARS 입력 대기 시간 안에 응답해야 한다. 두 함수 합산 응답 시간 목표는 2초 이내로 둔다 **[검증 필요]**. 이 시간 동안 앱에는 `selecting` 이 표시된다.
5. AI 모듈은 서버 저장소의 `interpreter.py` 에 정의된 `Interpreter` 프로토콜(위 7개 함수)을 구현한 클래스로 작성하고, 서버 환경변수 `INTERPRETER=모듈명:클래스명` 으로 지정한다. 서버 코드는 수정하지 않는다.
6. AI 모듈 호출이 예외·시간 초과로 실패하면 서버는 다음과 같이 진행한다. AI 모듈은 실패를 예외로 알리면 되고, 재시도는 하지 않는다.

| 함수 | 실패 시 서버 동작 |
| --- | --- |
| `summarize_goal` | "'목적' 업무를 찾아 드릴게요." 를 `goal_summary` 로 사용 |
| `classify` | 그 안내는 자막만 전송하고 계속 듣는다 |
| `score` | `request(clarification, unknown_prompt)` 로 사용자에게 묻는다 ("안내를 해석하지 못했습니다. 원하시는 메뉴를 말씀하거나 직접 골라 주세요.") |
| `answer_confirm` | 판단 불가(`null`)와 같이 `unknown_prompt` 재질문 |
| `merge_answer` | 사용자의 답변 문장을 새 목적으로 사용 |
| `summarize_result` | 결과 안내 원문을 `summary` 로, `key_info` 는 빈 배열 |
| `handoff_script` | "목적 건으로 연락드렸습니다." |

7. AI 모듈에는 사용자가 누른 키 값을 전달하지 않는다. `score` 의 `path` 와 `handoff_script` 의 `path_texts` 에는 안내에서 들은 선택지를 고른 단계만 카테고리·문장으로 넣으며, 직접 선택한 키(`key`)·이동 키·민감정보 입력은 제외한다. 앱에 전송하는 경로(PathStep)에는 직접 선택한 키가 그대로 남는다.
8. 선택지 정규화는 미리 정해 둔 단어 목록으로 하지 않는다. 매 ARS 단계마다 들은 선택지를 그 자리에서 카테고리로 정규화하고(`classify`), 사용자 목적을 그 단계의 카테고리에 맞춘다(`score`). 카테고리 이름 체계는 AI 담당이 정한다.

### 9.4 목 데이터

AI 모듈 구현 전까지 서버는 `mock_ai.json` 에 적어 둔 값을 그대로 반환하는 목 구현(`MockInterpreter`)으로 동작한다. 판단 로직은 없으며(정규화 결과·신뢰도도 미리 적어 둔 값), 시험용 가상 ARS(`sim_kb.json`)의 안내 문장과 아래 목적 문장만 처리한다. 목록에 없는 안내는 `kind=info`, 목록에 없는 목적은 모든 선택지 신뢰도 0 으로 처리한다. 목 구현의 `merge_answer` 는 답변 문장을 그대로 새 목적으로 사용하므로, 재질문에는 아래 목적 문장으로 답해야 시험할 수 있다.
