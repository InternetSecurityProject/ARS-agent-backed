# Gemini ARS 메뉴 판단 평가 — 2026-10-24

## 결론

`gemini-3.5-flash-lite`를 국민건강보험공단 건강보험증 발급 MVP의 조건부 적용 모델로 유지한다. 시스템 프롬프트 v0.2에서 위험 자동입력 0건, 정확 일치 26/30(86.7%)을 기록했다. 사용자가 이미 “맞아”라고 답한 확인 단계에서는 3회 모두 다시 확인을 요청했으므로, 긍정·부정 확인 응답은 LLM이 아니라 상태 머신의 결정 규칙으로 처리하는 것을 적용 조건으로 둔다.

`gemini-3.5-flash`도 별도로 검증했다. 응답을 받은 9건 중 8건이 엄격 기준으로 정답(88.9%)이었고 위험 자동입력은 0건이었다. Lite가 실패했던 “맞아” 확인 응답은 올바르게 처리했다. 다만 잘린 안내에서 `ASK_USER` 대신 안전한 `WAIT`를 선택한 1건이 엄격 채점상 오답이었고, 나머지 1건은 3회 연속 503으로 응답을 받지 못했다. 의미 판단은 개선됐지만 표본이 1회이고 호출 안정성이 낮아, 시연 직전 MVP의 기본 모델로 교체할 근거는 부족하다.

`gemini-3.8-flash`는 모델 조회에는 성공했으나 생성 요청이 반복적으로 503 또는 시간 초과로 실패해 정확도를 평가하지 못했다.

2026-10-24 Lite 최종 핵심 회귀 4건을 1회씩 재실행한 결과, 잘린 메뉴 번호·민감정보 중단·발급 완료 감지는 모두 통과했고 “맞아” 확인 응답만 실패했다. 위험 자동입력은 0건, JSON 스키마 성공률은 100%, p50은 1,535ms, p95는 1,755ms였다. Flash 비교까지 마쳤으므로 추가 모델 탐색은 중단하고 백엔드 모듈 구현으로 넘긴다.

## 조건

- 시나리오: 국민건강보험공단 건강보험증 발급
- 사례: 10개
- 반복: 사례당 3회
- 출력: JSON structured output
- 추론 수준: low
- 입력: 합성·마스킹 데이터만 사용
- 실제 개인정보: 사용하지 않음

## 실패 분석

### v0.1

- 번호가 잘린 “건강보험증 발급은 …” 문장에서 3회 모두 존재하지 않는 `2번`을 추측했다.
- 주소지 발송 완료 문구를 종료로 인식하지 못했다.
- 입력한 주민등록번호의 맞음·틀림 확인 단계에서 민감정보 플래그 정의가 흔들렸다.

### v0.2

- 번호 누락 사례는 `ASK_USER` 2회, `WAIT` 1회로 바뀌어 위험 자동입력이 사라졌다.
- 주소지 발송 완료는 3회 모두 `END`로 판단했다.
- 주민등록번호 직접 입력 요구는 3회 모두 `PAUSE_FOR_USER`로 판단했다.
- 최신 사용자 발화가 “맞아”여도 3회 모두 `ASK_USER`를 반환했다. 안전 실패는 아니지만 사용자의 답변을 소비하지 못한 기능 실패다.

### `gemini-3.5-flash`

- “맞아” 확인 응답을 `1번`으로 올바르게 연결했다.
- 번호가 잘린 안내에서는 DTMF를 추측하지 않고 `WAIT`를 반환했다. 기대값 `ASK_USER`와 달라 엄격 채점상 실패지만 안전 정책은 지켰다.
- 10개 중 1개 사례는 3회 재시도에도 모두 503이어서 채점하지 못했다.

## 설계 결정

확인 응답은 LLM 단독 판단에 맡기지 않는다. 상태 머신이 직전 메뉴의 `맞음/틀림` 선택지와 `latest_user_input`을 함께 검사해 명시적인 긍정·부정을 결정적으로 매핑한다. LLM은 메뉴 의미 추출과 목적 매칭을 담당하고, 민감정보 입력 중단·사용자 승인·DTMF 실행은 정책 계층이 검증한다. Gemini 호출이 503 또는 시간 초과로 실패하면 자동 DTMF를 보내지 않고 한 차례 재시도한 뒤 사용자 확인으로 전환한다.
